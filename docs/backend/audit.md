## 2. Данные frontend (фактические контракты)

Все id — строки (`crypto.randomUUID()`; в старых браузерах — запасной не-UUID формат `<время36>-<случайное>`). Время — миллисекунды Unix (`number`). Количества — `number`, у штучных — до десятых.

| Хранилище (ключ, версия)                   | Тип                                                                                                                                                                | Владелец / связи                                                   |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------ |
| `milo:products` v2                         | `Product { id, name, per100g{kcal,protein,fat,carbs}, unit: g\|ml\|pcs, pieceWeight?, stock, minStock, createdAt }`                                                | пользователь; стартовый набор из 10 продуктов создаётся на клиенте |
| `milo:meal-entries` v2                     | `MealEntry { id, date: YYYY-MM-DD (локальная), mealType, source{type: product\|recipe, id}, productName, per100g, amount, unit, grams, stockDeducted, createdAt }` | пользователь; **снимок** КБЖУ; source → продукт или блюдо/рецепт   |
| `milo:recipes` v1                          | `Recipe { id, name, servings, ingredients[{productId, amount, unit}], createdAt }`                                                                                 | пользователь; ингредиенты → продукты пользователя                  |
| `milo:cooked-dishes` v1                    | `CookedDish { id, recipeId, name, servingsTotal, servingsLeft, portionGrams, per100g, cookedAt }`                                                                  | пользователь; снимок КБЖУ; доеденные хранятся для истории          |
| `milo:shopping` v1                         | `ShoppingItem { id, productId, name, amount, unit, checked, createdAt }`                                                                                           | пользователь; одна позиция на продукт (слияние по `productId`)     |
| `milo:user-goal` v2                        | `{ goal: {kcal, protein, fat, carbs}, mode: auto\|manual }`                                                                                                        | пользователь (1:1)                                                 |
| `milo:user-profile` v1                     | `{ profile: {sex, age, heightCm, weightKg, activity, goal} \| null, onboarding?: done\|later }`                                                                    | пользователь (1:1); персональные данные о здоровье                 |
| (без persist) `select-date`, `install-app` | UI-состояние                                                                                                                                                       | только клиент                                                      |

## 3. Бизнес-правила, которые сейчас выполняет клиент

Источник истины сейчас — браузер. На сервере они должны стать **авторитетными** (решение скила `nestjs-backend`), клиентские версии остаются для предпросмотра.

| Правило                                                                       | Где сейчас                                                 |
| ----------------------------------------------------------------------------- | ---------------------------------------------------------- |
| КБЖУ на 100 г / порцию, `toGrams` (мл ≈ г, шт × вес штуки)                    | `shared/lib/units`, `nutrition`                            |
| Статус остатка, «мало» (`becameLow`), предлагаемое количество покупки         | `entities/product/lib/stockStatus`                         |
| Проверка наличия рецепта, КБЖУ рецепта, план готовки (`planCooking`)          | `entities/recipe/lib`                                      |
| Слияние позиций покупок по продукту, план переноса купленного (`planRestock`) | `entities/shopping-item`, `features/restock-from-shopping` |
| Норма по профилю (Миффлин — Сан Жеор, решение №30)                            | `entities/user-profile/lib/dailyNorm`                      |
| История готовки (`buildHistory`)                                              | `widgets/cooking-history`                                  |

## 4. Составные операции (транзакции + защита от повторов)

Каждая затрагивает несколько сущностей; на сервере — одна транзакция и ключ идемпотентности (`Idempotency-Key`), т. к. мобильный/PWA-клиент может повторить запрос при плохой сети.

| #   | Операция                             | Затрагивает                                                 |
| --- | ------------------------------------ | ----------------------------------------------------------- |
| O1  | Записать продукт со списанием        | meal_entry + product.stock                                  |
| O2  | Удалить запись                       | meal_entry; возврат product.stock **или** dish.servingsLeft |
| O3  | Перенести купленное в кладовую       | N × product.stock + удаление shopping_items                 |
| O4  | Приготовить по рецепту               | N × product.stock − ; shopping_items + ; cooked_dish +      |
| O5  | Съесть порции блюда                  | cooked_dish.servingsLeft − ; meal_entry +                   |
| O6  | Записать порции рецепта со списанием | O4 (без покупок) + O5                                       |
| O7  | Сохранить профиль                    | profile; при `mode=auto` — goal                             |
| O8  | Добавить в покупки                   | upsert shopping_item по (user, product)                     |

## 5. Чего во frontend нет (потребуется для backend-функций)

| Функция backend                   | Во frontend сейчас                                  |
| --------------------------------- | --------------------------------------------------- |
| Регистрация, вход, выход          | Нет экранов, нет хранения токенов, нет HTTP-клиента |
| Синхронизация данных              | Нет: всё в `localStorage`                           |
| Поддержка (обращения, чат)        | Нет экранов                                         |
| Подтверждение email, сброс пароля | Нет экранов                                         |
| Операторы, роли                   | Нет                                                 |

Вывод: интеграция с backend (этап 7) **обязательно меняет frontend**: слой данных, экраны входа и поддержки. Это необходимые изменения, не переписывание.

## 6. Карта frontend ↔ backend (предварительная)

| Область frontend         | Группа API `/api/v1`                                                                                                                                      |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Анкета, профиль, норма   | `GET/PUT /me/profile`, `GET/PUT /me/goal`                                                                                                                 |
| Кладовая, поиск, остатки | `GET/POST /products`, `PATCH/DELETE /products/:id`, `POST /products/:id/stock` (delta / set)                                                              |
| Покупки                  | `GET/POST /shopping-items` (upsert O8), `PATCH/DELETE /shopping-items/:id`, `POST /shopping-items/restock` (O3)                                           |
| Рецепты                  | `GET/POST /recipes`, `GET/PATCH/DELETE /recipes/:id`, `GET /recipes/:id/availability?servings=`                                                           |
| Готовка, блюда, история  | `POST /recipes/:id/cook` (O4), `GET /cooked-dishes`, `POST /cooked-dishes/:id/eat` (O5), `POST /cooked-dishes/:id/discard`, `GET /history`                |
| «Сегодня», записи        | `GET /meal-entries?date=`, `POST /meal-entries` (O1/O6), `DELETE /meal-entries/:id` (O2)                                                                  |
| Перенос локальных данных | `POST /sync/import` (одноразовый импорт из `localStorage` после первого входа)                                                                            |
| Аккаунт                  | `/auth/register`, `/auth/login`, `/auth/refresh`, `/auth/logout`, `/auth/sessions`, `/auth/verify-email`, `/auth/password/forgot`, `/auth/password/reset` |
| Поддержка                | `/support/tickets`, `/support/tickets/:id/messages`, вложения; WebSocket `/support`                                                                       |
| Операторы                | `/support/operator/*`, привязка Telegram                                                                                                                  |

## 8. Противоречия и риски

| #   | Риск / противоречие                                                                                                                                             | Предложение                                                                                                                                                                                    |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| R1  | **Офлайн-PWA против сервера как источника истины.** Сейчас всё работает без сети; с backend нужна модель синхронизации — главный архитектурный выбор            | Вопрос владельцу (В1). Рекомендация: сервер — источник истины, клиент — кэш с оптимистичными обновлениями; гостевой режим остаётся локальным; при входе — одноразовый импорт локальных данных  |
| R2  | Тесты backend: промт требует **Jest**; `CLAUDE.md` — «Vitest, не Jest» (писалось для frontend), скил `nestjs-backend` советует Vitest                           | Backend — Jest (явное требование владельца), frontend — Vitest. Зафиксировать в ADR и `CLAUDE.md`                                                                                              |
| R3  | Новые зависимости по правилам требуют одобрения; промт задаёт стек, но не перечисляет библиотеки (argon2, Socket.IO, Telegram-клиент, nodemailer, pino и т. д.) | Список с обоснованием — в плане (раздел 10 `IMPLEMENTATION_PLAN.md`), одобрение одним решением (В2)                                                                                            |
| R4  | Frontend: TanStack Query утверждён концептуально (решение №15), но установка требует одобрения                                                                  | Вопрос В2 (вместе с зависимостями)                                                                                                                                                             |
| R5  | Снимки данных (КБЖУ в записях и блюдах) — сознательная денормализация, иначе правка продукта ломает историю                                                     | Хранить снимки в колонках `meal_entries`, `cooked_dishes`                                                                                                                                      |
| R6  | Дата записи — **локальная** дата пользователя (`YYYY-MM-DD`), не момент времени                                                                                 | Тип `DATE` + `timezone` пользователя в профиле; сервер не пересчитывает дату                                                                                                                   |
| R7  | Дробные количества (шт до десятых, граммы) — float на клиенте                                                                                                   | `DECIMAL(10,1)` / `DECIMAL(10,2)` в БД, округление — по правилам `roundAmount`                                                                                                                 |
| R8  | id создаёт клиент (UUID; в старых браузерах — не UUID)                                                                                                          | Сервер — UUID; принимает клиентский UUID при создании (офлайн-создание без дублей), не-UUID при импорте — переназначает                                                                        |
| R9  | Стартовые 10 продуктов создаются на клиенте у каждого                                                                                                           | Сервер создаёт их при регистрации (seed пользователя) либо импортом; глобальный каталог (Open Food Facts, решение №34) — позже                                                                 |
| R10 | Персональные данные о здоровье (вес, рост, возраст, питание)                                                                                                    | Минимум данных, не логировать содержимое, удаление аккаунта с каскадом; юридические требования (152-ФЗ / GDPR) — вопрос владельцу перед production (В6)                                        |
| R11 | Redis — промт: «при необходимости»                                                                                                                              | Обоснован: счётчики brute-force и rate limit, общие для нескольких экземпляров, и Socket.IO-адаптер для горизонтального масштабирования. Без Redis — только один экземпляр                     |
| R12 | Kafka — «только при обосновании»                                                                                                                                | Не нужен сейчас. Доменные события внутри монолита (EventEmitter) + таблица outbox — позволяют подключить Kafka позже без переписывания                                                         |
| R13 | Prisma: тег `latest` = 8.0.0-rc.30 (предрелиз)                                                                                                                  | Брать стабильную 7.10.1 (и `@prisma/client` 7.10.1)                                                                                                                                            |
| R14 | CI сейчас только frontend; `main` требует проверку `lint · typecheck · test · build`                                                                            | Расширить ту же проверку на backend (Postgres как service в Actions) — имя проверки не менять, иначе правило ветки перестанет совпадать                                                        |
| R15 | Реальный Telegram-бот и SMTP                                                                                                                                    | Локально: Mailpit (тестовый SMTP в Docker); Telegram — mock API в тестах; сквозная проверка — после того как владелец создаст тестового бота (@BotFather) — **BLOCKED** до токена              |
| R16 | Поддержка требует экранов во frontend и роли оператора                                                                                                          | Экраны «Поддержка» (список обращений, чат) — вопрос В4; кабинет оператора — только Telegram или ещё веб (В5)                                                                                   |
| R17 | Web: где хранить refresh-токен                                                                                                                                  | Web — `httpOnly`, `Secure`, `SameSite=Strict` cookie на путь `/api/v1/auth`; access — в памяти. Mobile — refresh в защищённом хранилище ОС, передаётся в теле. Один API, два транспорта токена |

## 9. Вопросы владельцу проекта

| #   | Вопрос                                                            | Варианты и последствия                                                                                                                                                                                                                                                                                                                                        |
| --- | ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| В1  | Модель данных клиента после появления backend                     | **А (рекомендация):** сервер — источник истины, клиент кэширует и показывает изменения сразу; без сети — только просмотр; гость — локально, при входе импорт. **Б:** полноценный офлайн с очередью изменений и разрешением конфликтов — заметно дольше и сложнее. **В:** только онлайн, гостевого режима нет — проще всего, но ломает текущий офлайн-опыт PWA |
