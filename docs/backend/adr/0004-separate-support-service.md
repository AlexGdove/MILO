# ADR-0004. Поддержка — отдельный сервис

Статус: принято (2026-11-05). Связано: B-2, B-10, B-15. Уточняет ADR-0001 и ADR-0003.

## Контекст

Владелец хочет, чтобы поддержка работала, даже если основной сервер упал. Изоляцию даёт не любой «отдельный сервер»: на том же VPS или с общей базой поддержка падает вместе с основным сервером.

## Решение

- Отдельный сервис `support/` (workspace монорепо): NestJS 12 (ESM), PostgreSQL 17, Prisma 7, Jest — те же соглашения, что в `backend/` (формат ошибок, логи с `X-Request-Id`, проверка ENV).
- **Отдельный VPS и своя база.** Общих таблиц и синхронных вызовов между сервисами нет.
- **Свой анонимный ключ поддержки** (как ADR-0001: случайный секрет, в базе только SHA-256), не связан с ключом основного сервера. На устройстве два ключа; клиент хранит оба через `shared/lib/storage`.
- **Два Telegram-бота**: бот обращений — в `support/` (ответы операторов, outbox как в ADR-0003); бот модерации — в `backend/` (жалобы, скрытие рецептов).
- Фронтенд знает два адреса (`VITE_API_URL`, `VITE_SUPPORT_URL`); недоступность одного сервиса не ломает функции другого.

## Последствия

- Поддержка доступна при любом сбое основного сервера, его базы или VPS.
- Вдвое больше эксплуатации: два развёртывания, две базы и их бэкапы, два набора секретов, CI для обоих сервисов (в той же обязательной проверке, B-5).
- Из схемы `backend/` удаляются таблицы поддержки отдельной миграцией; `telegram_message_links` в основном сервере остаётся только для жалоб.
- Операторы работают в двух чатах (обращения и модерация) — можно один и тот же Telegram-аккаунт, но разные боты.
